# Primary Runtime 本地 Feed 与客户端命令拆分计划

## 文档分工

`docs/specs/primary-runtime-feed-v1.md` 定义 Feed 的 URL、签名、元数据、归档与客户端信任契约；这些共同契约以该规范为准。本计划定义本机开发 Feed 的命令、持久目录、导入、续签和验证流程；这些开发版实施细节以本计划为准。两者有冲突时先修正文档并保持实现一致，不把开发版流程推广为正式发布规则。

## 目标与范围

开发环境采用三段独立流程：GitHub Actions 构建 Runtime；本机 Feed 手动导入、验证并发布构建产物；开发版客户端从本机 Feed 获取签名配置，启动后自动检查并按需下载安装 Runtime。导入新版本后，运行中的 Feed 自动切换，客户端通过已有周期检查获取新版本；日常导入无需重启服务或客户端。

本计划只覆盖本机开发 Feed。正式安装包继续使用当前关闭的 Primary Runtime 配置；生产签名、公开 Feed 部署和正式发布不在本次范围内。Main 仍负责配置和清单验签、来源限制、归档校验、安装和激活；Renderer 不接触 Feed 地址、密钥或 Runtime 路径。不修改 Codex app server。

现有 Main 已有启动及周期检查、按需下载、健康验证、激活回滚和 bundled plugins 同步链路。本次复用该链路，不新增客户端下载器。开发 Feed 保留四个平台 final 构建的导入校验，以便沿用当前发布契约；本机运行时只下载当前平台的归档。

## 持久目录与发布边界

`services/primary-runtime-feed/var/development/` 保存下载缓存、开发签名与 TLS 材料、不可变归档仓库和元数据快照，目录保持 Git 忽略，私钥仅当前用户可读。归档按 `bundleVersion/target` 保存原 ZIP 及导入时验证的 provenance、工程证据；同一 URL 只允许同一 SHA-256。下载缓存与发布仓库分开，清理缓存不影响已发布归档。

每个元数据快照包含签名后的 `config.json`、频道清单和一份小型 `archive-index.json`。该索引列出到本次发布为止可访问的归档相对路径、版本、target、大小和 SHA-256；新快照沿用旧条目，只增加尚未发布的归档。同版续签沿用索引，不复制 ZIP。`current` 只指向一个完整快照，服务仅提供当前索引列出的归档；导入中断留下的未引用文件不能通过 HTTP 访问。索引是本机发布状态，不另设签名索引链或永久保留所有元数据快照的要求；已发布归档及其索引条目在本次范围内不清理。

现有 `publishRepository`、`validateReleaseTree` 和服务读取函数假设每个发布树都含完整归档；实施时将元数据与归档仓库分开验证和读取，不继续整树复制。导入先在同一文件系统暂存并完成校验，再原子放入新归档、写完新快照，最后原子切换 `current`。切换前失败保留旧 Feed；切换后服务校验新快照才采纳。异常退出后重启按 `current` 恢复；状态损坏时明确报错，不自动清除客户端信任记录。

## 命令与职责

| 入口 | 调整 | 最终职责 |
| --- | --- | --- |
| `desktop-app` 的 `dev:primary-runtime` | 删除；将 GitHub 下载和 Feed 组装迁到 Feed 工程 | 客户端开发命令不获取构建产物 |
| `desktop-app` 的 `dev:with-primary-runtime-feed` | 删除对外命令；保留并迁移测试使用的隔离 Feed 辅助代码 | 客户端开发命令不发布或启动 Feed |
| Feed 的 `dev:import` | 新增 | 手动获取、验证、签名并原子发布 GitHub 构建 |
| Feed 的 `dev:refresh` | 新增 | 需要时离线续签当前元数据；单次运行，不访问 GitHub |
| Feed 的 `dev:serve` | 新增 | 从持久目录提供回环 HTTPS Feed，不下载或签名 |
| `desktop-app` 的 `dev:local-feed` | 新增 | 读取公开连接配置，只启动使用本机 Feed 的开发版 Electron |
| `desktop-app` 的 `dev` | 保留 | 普通开发启动，不自动配置 Runtime Feed |

现有 Feed、release contract、Primary Runtime 真实运行及各类 E2E 测试保留；只更新迁移后的辅助代码和命令引用。各 E2E 仍使用隔离的暂存树、TLS 和 Feed fixture，不依赖开发者持久目录或已运行的 `dev:serve`。打包时写入产品配置的脚本继续保留。

## 实现步骤

1. **导入构建。** 将 `scripts/dev-primary-runtime.mjs` 的构建选择、下载重试和缓存逻辑移入 Feed 工程。修正当前把 `gh run view --json workflowName` 的显示名称与 `.github/workflows/primary-runtime-build.yml` 路径比较的问题：根据 `workflowDatabaseId` 查询 Actions workflow 的 `path`，自动选择和 `--source-run <id>` 均核对路径、成功状态及当前提交。默认选当前提交最新且包含四个平台 staging 产物的 final run；显式 run 也须属于当前提交。缓存命中时重新校验，不能只看文件是否存在。逐平台核对 run、版本、ZIP 摘要和大小、provenance 及工程证据，并调用现有跨平台完整验证器；缺失或不匹配的构建不得发布。完整工程验证只在导入时执行，续签不依赖当前 Git 工作树。

2. **归档不可变与原子发布。** 现有 final `bundleVersion` 由提交和平台决定；同提交的不同 run 不是新版本。导入时以当前归档索引判断已发布版本：同版本、同平台、同摘要可复用；已发布条目的摘要不同立即报版本冲突，不能覆盖旧 URL。仓库中未入索引的崩溃遗留文件可在锁内校验后复用或清理，不算已发布版本。新归档先写入临时路径并验证，再原子改名；快照写完并核对当前配置、清单、索引及其引用后，最后切换 `current`。旧归档始终保留以支持已经取得旧签名清单的客户端。重复导入和同版续签都不增加 ZIP 副本。此次不改变 GitHub Actions 的版本命名。

3. **签名状态与按需续签。** 开发签名密钥及序号持久保存在新的 Feed profile 中；导入和续签共用独占锁。发布前取持久序号与当前签名元数据序号的最大值，先原子预留更高序号，再签名并切换 `current`；异常退出允许跳号。首次建立新 profile 时从序号 1 开始，但 `dev:local-feed` 默认使用独立开发用户数据目录，不复用旧开发命令的信任状态。本次不迁移旧缓存中的私钥或信任记录，也不改变 Main 的信任记录格式。已有 profile 缺少签名密钥时不得原地生成新密钥；签名材料丢失或序号落后于客户端时明确报信任冲突，不自动重置。

   现有签发脚本生成的配置和清单有效期为 24 小时。`dev:refresh` 从 `current` 读取已签名清单及对应归档索引，核对当前四个 ZIP 的大小和 SHA-256，沿用原版本、URL、预算与其他发布字段，只更新时间和序号，生成新签名元数据快照并原子切换；不重新下载、不复制 ZIP、不重跑完整工程验证。到期后由开发者手动运行一次；本次不增加 `--watch`。过期时服务继续提供原签名字节，Main 依既有有效期校验拒绝安装并显示过期原因。

4. **独立服务与热切换。** `dev:serve` 默认绑定 `127.0.0.1:9443`。启动时校验当前配置和清单的签名、结构及索引格式，确认索引路径均留在归档仓库且对应常规文件存在、大小相符；旧归档不在每次启动或切换时全部重算哈希。请求处理使用一份已验证的元数据快照及归档索引；检测到 `current` 切换时，先验证新快照及本次新增归档的实际 SHA-256，再把元数据和索引作为一个状态替换。失败时继续服务旧状态并报告。服务只按索引提供旧 URL；客户端在下载完成后仍按签名清单的大小和 SHA-256 验证，能发现服务运行期间的意外改写。元数据过期不使旧归档 URL 失效。日常导入及续签无需重启服务。

5. **本地 TLS。** 首次建立 Feed profile 时生成只用于回环地址的开发 CA 与服务证书并持久保存；服务证书有效期为一年，CA 为五年。Main 仅在该精确回环来源的请求中使用公开 CA 证书，不更改全局 TLS 信任。`dev:serve` 只读服务证书和私钥，不持有签名私钥或 CA 私钥。证书失效时明确报错；重建 TLS 材料并重启服务及开发版客户端是低频维护操作。本次不做自动续证或运行中替换 TLS 上下文。

6. **客户端连接与隔离。** Feed 生成 `var/development/client-profile.json`，只包含精确 HTTPS 地址、频道、配置与清单公钥及 CA 证书绝对路径，不含私钥。`dev:local-feed` 校验 schema、回环来源、CA 文件和 HTTPS 可达性，再设置 Main 需要的 config URL、精确来源白名单和公开 keyring；清除继承环境中的直接归档、清单和本地 Runtime 根目录覆盖。缺失、无效或不可达时启动前报错，不回退到其他安装路径。

   开发入口默认使用固定、Git 忽略的独立用户数据目录，保留普通 `dev` 和正式版的用户数据及信任状态；此入口的项目和会话数据也与普通 `dev` 分开。该路径只由新开发入口传给 Main，并在 `app.setPath('userData', ...)` 前检查 `!app.isPackaged`；不直接复用未加此门禁的 E2E 环境变量。签名密钥或 Feed profile 丢失后，保留原目录并提示开发者显式建立新的隔离 profile，不自动删除旧信任状态。

7. **配对校验与版本语义。** 配置和频道清单经两次请求获取，可能跨越 Feed 切换。Main 先完成两者的签名、来源、频道和有效期校验，确认 `sequence` 相同且提交时仍有效，再选择版本；不一致时有限次重取整对元数据。配对失败不得写入任一新信任记录，也不得安装。成功后以一次原子写入接受 config 和 manifest 两条信任记录；原有 manifest 最高序号仍作为拒绝回退的下限，后续单独持久化失败中止本次安装，而已原子接受的 manifest 记录可供下次重试恢复。现有配置客户端在取得 config 后立即写信任记录的行为须随此步骤调整。切换发生在配对之后时，旧清单仍可从保留的旧 URL 下载归档。

   本地 Feed 以当前发布版本为期望版本：本机缺失或版本不同就安装，允许开发者通过切换仓库提交并导入对应 final 构建而有意回到旧版本；提交 SHA 形式的版本不作大小排序。同版续签只更新信任状态，不重新安装。保留 Main 的健康验证、激活回滚和插件同步失败的独立报告。开发版至少区分过期、验签失败、信任冲突及快照配对失败，向插件中心显示具体原因；本次不新增一组仅供本地 Feed 使用的稳定错误码。

日常启动：

```bash
npm --prefix services/primary-runtime-feed run dev:import
npm --prefix services/primary-runtime-feed run dev:serve
npm --prefix desktop-app run dev:local-feed
```

指定构建时给第一条命令添加 `-- --source-run <run-id>`。元数据过期时按需运行 `npm --prefix services/primary-runtime-feed run dev:refresh`。导入新版本只需重新运行 `dev:import`。只有导入需要 `gh` 登录和当前提交的成功 final 构建；服务、客户端启动及续签可离线进行。

## 验收与验证

- 命令契约确认客户端旧组合命令被移除；`dev:local-feed` 不调用 `gh`、不发布或启动 Feed；`dev:serve`、`dev:refresh` 离线可运行。
- 导入覆盖自动及指定 run 的工作流路径、提交和四平台产物校验，缓存被篡改、产物缺失、同 URL 不同摘要、重复导入及切换前失败；发布失败不改变 `current`。
- 发布和服务覆盖热切换前后旧归档字节与 URL 保留、未入索引的暂存文件不可访问、切换后崩溃重启、索引或新增 ZIP 损坏时拒绝采纳，以及导入与续签互斥。同版多次续签后归档数量和总字节数不增加。
- 续签覆盖 24 小时到期、手动离线续签恢复、归档摘要不符时拒绝续签，以及服务对过期元数据继续提供原签名字节。证书失效给出明确错误；本次不测试自动续证或热换证书。
- 客户端覆盖公开连接配置无效或 Feed 不可达、独立用户数据目录与正式版门禁、冷安装、持续运行时升级、同版续签不重装、有意回到旧提交、配对期间 Feed 切换及配对后下载旧归档。配对失败不写信任状态；配对成功后的两条记录原子提交，单独最高序号持久化失败时中止安装且可重试。验签、过期和归档哈希失败均不安装；插件同步失败不回滚已提交 Runtime。
- 继续运行 Feed 契约、`test:release-contract` 和真实 Feed E2E。冷安装不能代替升级验收。

## 已确定的约束

- 自动选择构建以当前仓库提交为准；显式 `--source-run` 也须属于该提交。四个平台的 final 产物须在导入时完整验证。
- 同版本不同归档字节不得取代既有发布；当前 Feed 版本是客户端期望版本，不按提交 SHA 排序。
- 元数据快照与不可变归档分开保存；旧归档按已发布索引持续可访问，同版续签不复制 ZIP。本次不做旧归档清理。
- 导入由本机用户手动触发；服务、客户端启动和手动离线续签不访问 GitHub。元数据到期由开发者按需续签。
- Feed 仅绑定回环 HTTPS；本地 CA 仅供 Main 到精确本机来源的连接使用。正式安装包不启用该开发配置。
- 进程异常退出后按 `current` 恢复，客户端拒绝不符的签名和归档哈希。本机开发 Feed 不承诺抵御同一用户改写已发布文件，也不承诺突然断电后的零回退；状态不一致时明确报错，不自动清除信任状态。
